<Layer kind="concept">

Map-reduce is the pattern that buys speed: split the work, run the pieces in parallel, combine. In LangGraph the split is a conditional edge that returns one **`Send`** per piece. Each `Send` becomes its own task in the next super-step, whose input is the payload it carries rather than the graph state; all of them run in that one super-step, their writes are combined by the key's reducer at the barrier, and the reduce node runs once, in the super-step after. The engine's runtime models `Send` exactly as LangGraph 1.2.14 does: <V of="conformance.sessions" fmt="int" /> sessions are checked checkpoint for checkpoint against the real library, including a map-reduce, a crash in one worker (with a checkpointer, its siblings' writes are kept and the resume re-runs only the failed worker), an interrupt in one worker, an empty fan-out and sends from two routers beside ordinary edges (the `Send` tasks' writes are applied after the edge-triggered tasks', in send order).

<span id="or-limits" />

Parallel on paper is not parallel in practice. Here a document of <V of="fanout.fans.0.chunks" fmt="int" /> chunks of <V of="fanout.fans.0.chunk_tokens" fmt="int" /> tokens is summarised chunk by chunk and the summaries reduced, against an endpoint with a limit of <V of="fanout.fans.0.rpm" fmt="int" /> requests and <V of="fanout.fans.0.otpm" fmt="int" /> output tokens a minute and a choice of input-token limits. The **width** is how many calls run at once: LangGraph's `max_concurrency` run setting caps the tasks of a super-step that run together.

- **Without a binding limit** (<V of="fan.200000.w.32.ms" fmt="dur" /> at width 32 and 200,000 input tokens a minute) the speed-up follows **Amdahl's law** exactly: the split and the reduce cannot be parallelised, the summaries are a fraction <V of="fan.200000.parallel_fraction" fmt="f3" /> of the one-at-a-time time, and width 32 gives <V of="fan.200000.w.32.speedup" fmt="f2" />× rather than 32×.
- **At 80,000 input tokens a minute** the curve bends: the workers need <V of="fan.80000.tin" fmt="int" /> uncached input tokens, the bucket holds 80,000 and refills at 80,000 a minute, so the later calls wait for capacity (hatched). Width 16 reaches <V of="fan.80000.w.16.speedup" fmt="f2" />×, not Amdahl's <V of="fan.80000.w.16.amdahl" fmt="f2" />×, and widening further buys nothing.
- **At 40,000** the bucket is the whole story: every width from 2 up finishes in <V of="fan.40000.w.2.ms" fmt="dur" /> (<V of="fan.40000.w.2.speedup" fmt="f2" />×), under the bucket's bound of <V of="fan.40000.w.2.ceiling" fmt="f2" />×. More parallelism only makes more calls wait.

The lesson generalises: a fan-out is limited by the slower of two ceilings, the serial part of the work and the rate at which the endpoint will accept tokens. Which one binds is a matter of arithmetic you can do before you build it.

</Layer>

<Callout kind="illustrative">

The document, the chunk and summary sizes, the limits (a deliberately small, workspace-style limit; the Claude API's standard tiers are far higher) and the latency profile are illustrative. The rate limiter follows the Claude API's [documented](https://platform.claude.com/docs/en/api/rate-limits) token-bucket scheme (capacity equal to the per-minute limit, replenished continuously; cache reads do not count toward input tokens), with a client that waits for capacity instead of collecting 429 errors; output tokens are charged when a call ends. No failures are injected in this chapter (chapter 7).

<Layer kind="maths">

<span id="or-amdahl" />

Let $T_1$ be the time one call at a time and $f$ the fraction of it that can run in parallel (everything but the split and the reduce). With $N$ calls at once and nothing else in the way, $T_N = T_1\big((1-f) + f/N\big)$: Amdahl's law (G. M. Amdahl, _Validity of the single processor approach to achieving large scale computing capabilities_, AFIPS 1967, doi:10.1145/1465482.1465560), which the engine's tests check the simulation reproduces exactly when the limits are out of reach.

A token bucket with capacity $B$ and refill rate $r$ admits at most $B + r\,t$ tokens by time $t$. To admit all $\sum_i n_i$ uncached input tokens, the last call cannot start before $T_{\text{bucket}} = (\sum_i n_i - B)/r$, so $T_N \ge T_{\text{bucket}}$ whatever $N$ is. At 40,000 tokens a minute the calls need <V of="fan.40000.tin" fmt="int" /> uncached input tokens, so the bound is (<V of="fan.40000.tin" fmt="int" /> − 40,000) at 40,000 a minute, <V of="fan.40000.bound_ms" fmt="dur" />, against <V of="fan.40000.t1" fmt="dur" /> one call at a time. The same bound holds for requests and output tokens; the binding one is the largest. The engine's tests also check that no window of the simulated run admits more input tokens than $B + r\,\Delta t$.

</Layer>

<Layer kind="code">

The admission rule of the discrete-event simulation, cut from the vendored engine (`des.ts`):

```ts
if (buckets.rq + EPS >= 1 && buckets.it + EPS >= ni && buckets.ot + EPS >= 0) {
```

And how the graph runtime turns a router's send leaf into `Send` packets (`graph.ts`):

```ts
for (const item of (state[g.over] ?? []) as unknown[]) {
  const arg: Obj = { [g.as]: clone(item) };
  for (const k of (g.with ?? []) as string[]) arg[k] = clone(state[k] ?? null);
  out.push({ send: g.send, arg });
}
```

**In production.** The same map-reduce in LangGraph itself: a conditional edge returns one `Send` per item, every `worker` runs in the same super-step with its own input, and the reducer on `answers` (`operator.add`) appends their writes before `reduce` runs once:

```python
import operator
from typing import Annotated, TypedDict

from langgraph.graph import END, START, StateGraph
from langgraph.types import Send


class State(TypedDict):
    questions: list[str]
    answers: Annotated[list[str], operator.add]  # each worker's write is appended


def fan_out(state: State) -> list[Send]:
    # one Send per item: each runs `worker` with its own input, in the same super-step
    return [Send("worker", {"question": q}) for q in state["questions"]]


def worker(arg: dict) -> dict:
    return {"answers": [f"answer to {arg['question']}"]}


def reduce(state: State) -> dict:
    return {"answers": [f"{len(state['answers'])} answers merged"]}


g = StateGraph(State)
g.add_node("worker", worker)
g.add_node("reduce", reduce)
g.add_conditional_edges(START, fan_out, ["worker"])
g.add_edge("worker", "reduce")
g.add_edge("reduce", END)
app = g.compile()

print(app.invoke({"questions": ["q1", "q2", "q3"], "answers": []})["answers"])
```

Run here with LangGraph 1.2.14, the version this site's runtime is checked against; it prints `['answer to q1', 'answer to q2', 'answer to q3', '3 answers merged']`.

<Remember>

- In LangGraph a fan-out is a conditional edge returning one Send per piece; all of them run in one super-step.
- The speed-up is capped by Amdahl's law: the serial part of the work.
- It is also capped by the endpoint's token bucket: the time to admit every token beyond its capacity.
- Which ceiling binds is arithmetic you can do before you build it.
